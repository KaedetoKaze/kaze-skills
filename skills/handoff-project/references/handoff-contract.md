# 交接内容契约

## 发现现役文件（仅在需要读取或写入文件时）

按以下顺序定位现役文件：

1. 用户明确指定的文件。
2. 当前项目规则、文档索引或状态阅读路由明确指向的 handoff。
3. 已存在且仍被项目使用的交接文件，常见位置依次为 `facts/handoff.md`、`.agents/handoff.md`、`docs/handoff.md`、`HANDOFF.md`。

多个候选同时存在时，依据规则引用、最近维护状态和现役任务选择；无法确认唯一真身时先向用户说明候选，不创建新文件。现有文件可以作为恢复资料，只有主流程中的持久化条件成立且项目规则允许时才写入。确需新建文件但没有约定位置时，先确定项目允许的位置；不得仅因缺少现役文件就在根目录创建 `HANDOFF.md`。保持项目原有语言、标题和章节风格。

## 必备语义

回复或现役交接文件应按任务需要回答：

- **模式与核验时间**：说明处于中间状态还是阶段收尾，使用绝对日期；写入文件时可标为 `checkpoint` 或 `knowledge-closed`。
- **当前目标**：期望结果、本阶段边界，以及用户新请求带来的覆盖。
- **任务状态**：明确区分 `DONE`、`PARTIAL`、`TODO`、`DEFERRED`、`OUT-OF-SCOPE`。
- **当前停点**：最后正在处理的对象、已观察到的结果，以及尚未完成的那一步。
- **验证状态**：运行过什么、结果如何、哪些尚未验证、为什么未验证。
- **阻塞与待决定**：解除阻塞需要的输入、权限、外部状态或用户选择。
- **失败路径与陷阱**：只记录足以避免重踩且尚未进入正式知识的内容，并注明重试条件。
- **下一动作**：第一个可执行动作、后续顺序及本阶段完成判据。
- **继续阅读**：指向规则、活动规格、关键代码、决策和正式文档。
- **Git 现场**：仅在有助于恢复时记录当前分支和未提交范围；恢复时以实时 Git 状态重新核验。

空章节不必保留。交接所需信息应在当前回复、明确引用的现役文件或正式来源中可获得，不能依赖旧会话。

```md
1. 首个动作。
2. 后续动作。

```

只在需要写入文件时参考此骨架。已有项目采用其他结构时，保留原结构并满足上述语义，不为了套模板制造大范围改写；回复交接无需套用文件格式。

## 去重与可信度

- 稳定机制放正式文档；生效决策放决策记录；活动实施计划放规格或任务系统；历史过程交给 Git、归档或事件文档。
- 交接只携带现场：停点、未完成状态、临时阻塞、验证边界和下一动作。
- 事实可信度依次来自当前仓库与运行证据、现役正式文档、交接记录。用户决定工作方向和范围。
- 验证结果注明日期和覆盖面。无法重跑时写“未重跑”，不将历史结果升级为当前结果。

## RESUME 报告

恢复说明按以下顺序输出；是否等待确认由用户本次请求决定：

1. 当前目标与范围。
2. `DONE`、`PARTIAL`、`TODO` 摘要。
3. 当前停点和验证边界。
4. `DEFERRED`、`OUT-OF-SCOPE`、阻塞与待决定事项。
5. 已有交接记录与实时仓库的差异（如适用）。
6. 建议的首个动作及其完成判据。

用户只要求恢复说明时，结尾使用明确确认门，例如：

```text
如果以上恢复结果正确，我将从“……”开始；你也可以调整目标、顺序或范围。
```

用户只要求恢复说明时，确认前只执行读取、搜索、状态检查和其他无副作用核验；用户明确要求核验后直接继续时，说明后按已授权范围继续。
