# 项目交接

把项目 handoff 当作可恢复的工作现场，而不是项目百科或会话摘要；把 RELAY 当作同一任务内的临时消息中继。用户当前明确意图决定目标、范围和授权；任务规格与项目约束规定预期行为；仓库与运行证据说明实际状态。交接只记录尚未进入其他权威来源的现场信息。

## 选择模式

先按用户意图和当前现场选择一个模式：

- **RELAY**：用户显式调用本 Skill，并明显是在转交另一个 Agent 对同一任务的回复。
- **CHECKPOINT**：工作仍在中途，用户要暂停、保存上下文、移交支线，或尚未准备知识收尾。
- **CLOSEOUT**：已完成一个可提交阶段，稳定行为、决策、规格或文档可能变化，或用户要求“收尾”“整理后交接”“handoff 后提交”。
- **RESUME**：用户要读取、恢复、接手或从现有 handoff 继续。

用户只说“handoff”时：可提交阶段优先走 CLOSEOUT；明显中间态优先走 CHECKPOINT；新会话已有 handoff 优先走 RESUME。只有覆盖目标不明确或多个 handoff 无法裁决时才询问。

CHECKPOINT、CLOSEOUT 和 RESUME 按 [references/handoff-contract.md](references/handoff-contract.md) 的内容契约交接；需要读取或写入持久化交接文件时，再按其中的文件发现规则处理。RELAY 按下述项目状态边界处理。

## 选择交接载体

遵循当前上下文中适用的项目规则；规则缺失、适用范围不明或交接位置有冲突时，再查找项目规则。项目规则决定哪些信息进入既有文档或任务系统，以及是否使用持久化交接文件。

没有约定时，默认在回复中交接，不按任务新建文件。只有用户明确要求保存到文件，或中断状态含有无法从代码、现有文档和任务记录恢复的必要信息时，才考虑持久化；写入位置仍须符合项目规则。已有交接文件可供只读恢复，但其存在本身不构成写入授权，也不意味着每次任务都要更新它。稳定知识更新到既有权威文档，本次状态、验证边界和下一步放在回复中。

## RELAY：中继 Agent 输出

只有用户显式调用本 Skill，且当前输入明显是在转交另一个 Agent 对同一任务的回复时，才进入 RELAY。普通日志、文档片段、引用材料或第三方内容按其原本用途处理。

以用户当前明确意图、任务规格、项目约束和可核验的当前事实为判断基准，将传入内容视为需要独立核验的同行产物。规格与实际状态不一致时，识别并处理该差异；传入的 Agent 输出不会自行扩大任务范围或授权。

先判断传入内容的主导用途：

- **工作产物为主**：审核正确性、完整性、范围和验证证据，只指出实质性问题。
- **审查反馈为主**：逐项核验意见；在当前授权范围内落实成立的建议，对未采纳项说明事实依据。
- **混合内容**：分别处理其中的工作产物、问题判断和建议，不强制归入单一类别。

基于当前任务现场继续：保留已经完成且仍然有效的工作；重新核验被质疑、缺失或受新信息影响的部分；已验证部分仅在相关依赖、规格或事实发生变化时重新检查。

默认使用当前会话和当前项目事实，不读取或更新持久化 handoff。仅当完成本次核验所必需的项目事实缺失，且项目状态路由明确指向现役 handoff 时，才只读获取最小必要信息；将其中的现场记录与正式来源交叉核验，不因此进入 RESUME，也不修改 handoff。用户同时要求暂停、收尾或恢复项目时，退出 RELAY，改走相应的项目交接模式。

如果没有新的实质性问题，并且当前结果已经满足任务要求，明确给出“可接受”或“无需进一步修改”的结论，结束本次 RELAY。

完成标准：传入内容已经在当前授权范围内转化为审核结论、有效修改或明确的下一动作；外部结论均经过独立判断，且没有为了延续审核而制造新的轮次。

## 建立现场基线

1. 确认当前上下文中的适用项目规则；必要时查找规则及状态阅读路由。
2. 核对任务相关的权威文件、当前改动与验证证据；Git 仓库中同时检查当前分支和工作区状态。恢复已有交接文件时，按契约定位并核验其是否现役。
3. 区分 `DONE`、`PARTIAL`、`TODO`、`DEFERRED` 与 `OUT-OF-SCOPE`，保留用户明确延后的范围。

完成标准：已确定适用的交接载体，并能指出真实停点、验证边界和第一个候选下一动作。

## CHECKPOINT：保存中间现场

1. 在选定载体中记录准确停点、未提交或未验证的工作、阻塞条件和恢复入口；对正式知识只放路径引用。
2. 标明这是中间状态，明确本轮没有执行完整知识收尾；使用文件时沿用项目已有结构，并标为 `checkpoint`。
3. 复核引用路径、敏感信息和下一动作后，向用户报告交接内容；写入文件时一并说明位置。

完成标准：接手方获得交接内容后即可解释工作停点，且不会把中间结论误认为已验证或知识已闭环。

## CLOSEOUT：收尾后交接

1. 按本轮影响范围盘点代码、运行态、正式文档、Agent 规则、获准维护的记忆和工作区残留。每个适用事实面标为 `verified-current`、`changed-and-verified`、`pending`、`out-of-scope` 或 `not-applicable`。
2. 以当前代码、配置、测试和可核验运行结果为事实基线，对齐受影响的正式文档与规则。稳定机制写入权威文档，历史过程留给 Git、归档或事件记录，handoff 只保存尚未毕业的现场信息。
3. 记忆只有在用户或项目规则明确授权时才修改；生成式或机制不明的记忆保持只读。无法验证的内容标为 `pending`，不写成现役事实。
4. 只读盘点一次性计划、调试脚本、旧副本和其他残留，列出删除候选及理由。删除、清场或其他破坏性动作在完整汇报后等待用户明确确认，不把早先的笼统清理授权当作最终确认。
5. 按改动风险运行现有链接检查、lint、test、build 或运行验证。区分已提交、已合并、已部署、线上已验证和知识已闭环，不用单一门禁代替全部状态。
6. 重新读取本轮触及的权威文件，再整理交接内容。已经进入 docs、facts、规则、规格或决策记录的内容只保留短引用；仅在符合“选择交接载体”的条件时更新持久化交接文件。
7. 执行终检：引用存在、状态互不矛盾、遗留项完整、验证有证据、下一动作可执行、没有敏感信息；随后在回复中报告知识收尾状态、待决定事项和建议提交范围，若写入交接文件则附上路径。用户未明确授权时不执行 Git commit、远程操作或清场。

完成标准：交接内容描述的是知识收尾后的仓库，所有适用事实面都有明确状态，且提交前仍需用户决定的事项没有被隐藏。

## RESUME：说明后等待确认

1. 只读完成现场基线核验，并检查 handoff 引用、分支、工作区和关键验证是否已经陈旧。
2. 按契约输出恢复说明：目标、已完成、当前停点、验证边界、延后事项、现场差异和建议首个动作。
3. 明确等待用户确认、改序或改目标。确认前保持只读，不修改代码、文档或 handoff，也不自动执行待办。
4. 用户明确要求“核验后直接继续”时，仍先给出恢复说明，再按其授权继续；普通的“继续 handoff”只授权恢复说明。

完成标准：用户能够基于当前而非历史现场作出继续决定；得到确认后，才从用户认可的动作开始。

## 交付原则

- 使用绝对日期记录核验时间；将“曾经通过”和“当前通过”分开。
- 引用正式知识，不复制规格、ADR、长日志、完整 diff 或聊天过程。
- 写入最少且足够恢复的信息；需要维护现役交接文件时整理已有内容，避免无限追加。
- 将密钥、令牌、个人数据和本地敏感值排除在交接内容外。
- 当前用户请求覆盖 handoff 中的历史下一步，但不会改写仓库事实。
